# Parameterized / Oracle Tester — Feature Plan (extends Feature 4)

> Status: **PLANNING** — brief reviewed (2026-10-19); not implemented. This is a design plan for review.
> Branch: `william-autoTester` (forked from the merged `william-testParamaters`, which already
> contains the current property-based Feature 4). The existing Feature 4 code is **not** changed
> by this plan unless the team decides to merge the two modes.

## 1. Goal and motivation

Add an **opt-in, instructor-powered** mode to Feature 4 that generates tester inputs
parameterized from a spec and compares the student's output against an **instructor reference
solution** (a model answer) — LeetCode-style hidden tests, done offline.

Why extend Feature 4 rather than stay property-based:
- Today's Feature 4 checks **invariants** the grader re-derives from the question definition. That
  needs no oracle, but it is weak for questions where the "definition" is hard to re-derive
  generically (e.g. Q2a/Q2b currently only probe *non-fixed* surnames/courses because the grader
  cannot compute a generic expected average/top-student).
- Handing the instructor an **oracle** (their own reference solution) lets us test *every* input
  and is the most robust anti-hardcoding check. It is **opt-in**: if the instructor supplies a
  reference + spec, we use it; otherwise the existing property-based mode still runs.

This satisfies the bonus idea: *"Automatic or parameterized generation of tester files to reduce
hard-coding risks,"* with the instructor providing the answer key only when they choose to.

### 1.1 Brief alignment (verified 2026-10-19 against `CS102-Project-Auto Grading System.pdf`)
- **Named bonus (p.6, §5):** *"Automatic or parameterized generation of tester files to reduce
  hard-coding risks"* is listed verbatim as an example bonus feature. This feature is therefore
  squarely on-brief, not an invented extra.
- **Problem it solves (p.5, Step 2):** the brief states instructors *"must design new test cases that
  differ from those in the original question files to prevent hard-coding"* because a student who
  hard-codes against the shipped question file can *"incorrectly receive full marks."* A seeded
  generator that produces varied inputs is exactly the mitigation the brief asks for.
- **No new external dependency required (p.3):** *"Only the use of external free or open source
  libraries is allowed."* The generator uses only `java.util.Random` (JDK stdlib); the spec format
  is dependency-free (see §3.1). No network/online call is made — fully offline, satisfying the
  "restricted/isolated" grading context.
- **OOP & quality map to the top rubric band (p.6, 25–30):** good modularization, methods do one
  thing, externalized configuration, clear packages, clean design. The design below isolates
  generation, oracle execution, comparison, and provider wiring into separate classes/modules.
- **AI-attribution is REQUIRED by the brief (p.3):** every AI-assisted method needs a
  `// Generated by <tool>` comment, plus an *"AI Use"* section in the presentation appendix.
  Per the team rule, **William adds these manually before submission** — the agent will NOT
  auto-inject them. Every team member must be able to explain this code at the demo (p.3).

## 2. Design overview

```
 per-question spec (seeded)            instructor reference solution
        |                                      |
        v                                      v
 Grader-side GENERATOR  ──builds inputs──▶  [isolated JVM]  ──expected output
        |                                      |
        |  (same generated inputs)             |
        v                                      v
 Student subprocess ──actual output──▶  COMPARATOR ──▶ PASSED / FAILED / ERROR
```

- **Seeded**: the same seed reproduces the same inputs → grades are deterministic and re-gradable.
- **Black-box**: the student receives only the generated inputs (plain argument values, or a
  generated data file), never the generator classes or the reference solution.
- **Isolated oracle**: the reference solution runs in a *separate* process/classloader from the
  student, so the student code cannot see or depend on it.

## 3. Components

### 3.1 Input spec (per question)
A small declarative spec describing each argument's generator and the number of trials. To stay
**dependency-free** (brief p.3: only free/OSS libs allowed) and showcase OOP, the generators are
**grader-side classes** implementing a common `Generator` interface (Strategy-style) — this matches
your `RandomInt` / `RandomString` idea and needs no parser or external library:

- `RandomInt {min, max}`
- `RandomString {minLen, maxLen, charset?}`
- `RandomDouble {min, max}`
- `RandomBool`
- `RandomList {size{min,max}, items[...]}` (recursive; items carry weights)
- Possibly `RandomElement {values[...]}` and `Fixed {value}` for mixing known edge cases.

The spec itself is expressed via a **fluent Java builder** (type-safe, no file format) and, optionally,
persisted to a minimal JSON/properties file loaded at runtime (hand-rolled parser; an OSS parser such
as Jackson/SnakeYAML is permitted only if a richer format is later desired). Starting point is the
Java builder; file loading is added if time allows.

Example (Q1b), as a builder:
```java
specFor("Q1b")
  .method("getSumOfEvenIntegers", ArrayList.class)
  .trials(25).seed(42)
  .arg(listOf()
         .size(0, 12)
         .item(RandomInt.of(-100, 100), 0.5)
         .item(RandomString.of(1, 8),   0.2)
         .item(RandomDouble.of(0, 100), 0.2)
         .item(RandomBool.of(),         0.1))
  .oracle(referenceOf("Q1bReference", "getSumOfEvenIntegers", ArrayList.class));
```

### 3.2 Generator (grader-side)
Reads the spec + seed and produces the argument values for each trial. Two delivery options, both
black-box:
- **In-memory**: build the argument objects and pass them to the student method via reflection
  (same mechanism as today's `DynamicRunner.invokeStatic`). Student code unchanged.
- **File-based**: write generated inputs to a plain data file the student's method reads
  (more LeetCode-like; matches existing `personstester.txt`/`studentstester.txt` contracts).

The generator classes (`RandomInt`, etc.) live in the **grader**, never on the student classpath.

### 3.3 Reference-solution oracle (instructor-provided)
The instructor supplies a reference implementation (e.g. `Q1bReference.java`) with the same
signature as the student method. It is compiled and executed **in an isolated JVM** (its own
subprocess, its own classpath) on the *same* generated inputs, producing the expected output.

Isolation options to evaluate:
- Separate `CaseExecutor` run with a reference-only classpath (simplest, mirrors student execution).
- Separate classloader inside the grader JVM (faster, but must guarantee no leakage).

### 3.4 Comparator / result token
For each trial, compare student output vs reference output using a per-type equality rule
(primitive equality; for `Shape`/objects, parse `toString()` like today's `Q3` handling, or use
`equals`/serialization). All trials must match → `PASSED`; any mismatch → `FAILED` with the
offending trial's diff printed to stderr. Token stays `PASSED`/`FAILED`/`ERROR` (≤ 16 bytes,
pipeline-capped).

### 3.5 Integration into the pipeline
Add a `ParameterizedTesterProvider` that emits cases from the spec, and merge it into
`CombinedTestCaseProvider` **alongside** the existing `DynamicTestCaseProvider` (property-based).
A per-question config flag selects the mode: oracle (if a reference + spec exist) or property-based
(fallback). No change to the current Feature 4 behavior when no spec/reference is supplied.

## 4. Instructor workflow (opt-in)
1. Instructor writes a per-question input spec (or reuses a template).
2. Instructor provides a reference solution for the question.
3. Both are placed in a documented location; the pipeline detects them and activates oracle mode
   for that question. Without them, the question keeps the existing property-based dynamic tests.

## 5. Constraints and open questions (resolve before coding)
Resolved by the brief review (2026-10-19):
- **Feature is explicitly on-brief:** *"Automatic or parameterized generation of tester files to
  reduce hard-coding risks"* is a named bonus (p.6, §5), and p.5 Step 2 states instructors must
  create *different* test cases to avoid hard-coding — this feature is the automated form of that.
- **No new dependency / offline:** brief p.3 allows only free/OSS libs; the generator uses only JDK
  `java.util.Random` and the spec is dependency-free (§3.1). No network calls. An OSS parser is
  permitted only if a richer spec format is later desired.
- **AI-attribution is mandatory (brief p.3):** every AI-assisted method needs a `// Generated by
  <tool>` comment and the deck needs an *"AI Use"* appendix. Per team rule, **William adds these
  manually before submission**; the agent will not auto-inject them. Team must be able to explain
  the code at the demo.
- **Submission/packaging:** repo already uses Maven (`src/main/java`, p.2/p.3); no change needed.
  Timeouts already isolate non-terminating programs (p.5 Step 3) via `CaseExecutor`.

Still to decide during implementation:
- **Reference isolation:** confirm the chosen isolation method keeps the reference solution off the
  student classpath (separate subprocess is simplest and mirrors student execution).
- **Comparator for complex types:** define equality for `Shape` and other objects (toString parse
  vs `equals`) before implementation — reuse today's Q3 `toString` parsing approach.
- **Reproducibility:** seed management so re-grading is identical across runs.
- **Scope of first cut:** decide whether to ship the file-loaded spec (JSON/properties) or ship the
  Java-builder spec first; recommend builder-first, file-loading later.

## 6. Phased implementation checklist (no code yet)
1. Read brief PDF; finalize constraints; get plan approval.
2. Spec format + `RandomInt`/`RandomString`/… generator classes (grader-side) + tests.
3. Generator → argument builder (in-memory and/or file-based) + tests.
4. Reference-solution isolated runner + comparator + tests.
5. `ParameterizedTesterProvider` + `CombinedTestCaseProvider` wiring + config flag.
6. End-to-end harness (correct reference → PASSED; hard-coded student → FAILED) across seeds.
7. Docs: update `HOW_THIS_FEAT_4_WORKS.md` / feature summary; if moved to DONE, create
   `parameterized_tester_architecture.md` with OOP notes + slide talking points (per completion gate).

## 7. Validation / evidence plan
Reuse the `scratch/verify.sh` style harness: for each question and seeds 7/42/99, a correct
reference implementation → `PASSED`; a memorized/hard-coded implementation → `FAILED`. Plus a
clean `mvn clean verify` (or the JDK-only launcher used in this repo) before any DONE claim.

## 8. Rubric & bonus alignment (brief p.6)
- **Bonus marks** (§5): awarded on *usefulness, correctness, design quality*. This is a named bonus
  and directly addresses the hard-coding risk the brief calls out in Step 2 — high usefulness.
- **Code band 25–30:** good modularization (separate `Generator`, `Spec`, oracle runner, comparator,
  provider classes — SRP), methods do one thing, **configuration externalized** (seed/trials/spec
  per question, not hard-coded), clear packages, clean OOP design.
- **Application band 25–30:** handles a complex scenario (anti-hardcoding across all inputs, not just
  the shipped question file) robustly; integrates into the existing pipeline so instructors get varied
  tester inputs automatically.
- **Defensible at demo/Q&A:** the design is explainable (generator → reference oracle in isolated JVM
  → comparator), and the team can articulate the algorithm trade-offs (property-based vs
  reference-based) required by the presentation rubric.
